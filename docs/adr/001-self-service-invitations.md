# ADR-001: 自助邀请与房间生命周期

- 状态: accepted
- 日期: 2026-09-09
- 相关组件: `Room`、`RoomStore`、`RoomManager`、`WatchTogetherService`、嵌入式 Watch Together 页面

## 背景

当前房间只能由管理员直接指定两名参与者创建。普通用户可以查看、加入和退出已经存在的房间，但缺少在不暴露全站用户目录的情况下邀请另一位用户的流程。现有房间仍严格要求两名成员，`Joined` 只表示暂离状态，退出不会解除成员归属。

## 问题

自助邀请需要在第二位用户接受之前保存一个待处理意图，并在接受时一次性完成身份、成员占用、房间创建和邀请消费。服务重启、重复接受、并发接受、过期和持久化失败都不能留下半个房间或错误消费邀请。

## 可选方案

1. 把待接受邀请写入 `rooms.json`，启动时恢复。
2. 使用独立持久化文件保存邀请码和状态。
3. 只在运行时保存待接受邀请，重启后统一失效。

## 最终选择

选择方案 3，首版不引入邀请持久化格式。

- 任意已认证用户都可以创建待接受邀请；创建者不能同时接受自己的邀请。
- 邀请只保存邀请码的 SHA-256 校验值、创建者、房间名称、创建时间、过期时间和状态。明文邀请码只在创建响应中返回一次。
- 邀请有效期为 15 分钟，只能成功消费一次。创建者可撤销并重新生成邀请码；每位创建者最多保留 3 个有效邀请，全局最多保留 100 个。
- 接受者不通过用户目录选择。任何其他已认证用户都可以输入邀请码，服务端在同一一致性边界内检查邀请、身份和成员占用。
- 接受成功后创建一个完整双人房间，并将创建者作为 `PrimaryUserId`、同步通知目标和 `CreatorUserId`。自助房间标记 `IsSelfService=true`；现有管理员创建的房间保持 `false`。
- `CreatorUserId` 是房间创建者身份，`AdminUserId` 继续作为现有运行时命令和提示的稳定目标。自助房间两者初始相同，但权限判断不得把 `AdminUserId` 当作普通用户的管理员授权。
- 只有管理员可以创建旧式指定成员房间；自助房间的创建者或管理员可以结束房间。现有退出语义保持不变，退出只表示暂离，永久结束仍使用删除房间操作。
- 服务重启后邀请码全部失效并从内存中丢弃，页面显示可操作的失效提示。现有 `rooms.json` 房间继续正常恢复。
- 邀请码尝试按已认证用户限制为每分钟 5 次，全局限制为每分钟 100 次；失败响应使用稳定的“邀请码无效或已过期”分类，不泄露创建者或房间存在性。

## 一致性与失败处理

邀请管理器在接受操作上串行化同一进程内的请求。校验通过后先调用房间管理器的原子自助创建路径，房间持久化成功才移除邀请；成员已占用、房间写入失败或运行时未就绪时保留邀请，允许用户重试。并发接受只有一个请求可以创建房间并消费邀请码。

邀请码管理器是运行时对象，由 `WatchTogetherEntryPoint` 与房间管理器一起创建和释放。它不参与 `SyncEngine` 的状态机，也不改变 Session、Item、Barrier、Pending 或远控恢复规则。

## API 边界

- `POST /WatchTogether/Invitations`：创建邀请，返回一次性明文 `Code` 和过期时间。
- `GET /WatchTogether/Invitations`：只返回当前用户创建的有效邀请元数据，不返回邀请码明文。
- `DELETE /WatchTogether/Invitations/{Id}`：由创建者或管理员撤销邀请。
- `POST /WatchTogether/Invitations/{Code}/Accept`：由另一位已认证用户接受邀请并返回新房间摘要。
- `DELETE /WatchTogether/Rooms/{Id}`：管理员可结束所有房间；自助房间创建者可结束自己的房间。

接口只返回当前用户相关的邀请和房间摘要，不提供全站用户目录，不返回 Token、原始用户 ID、服务器路径或底层异常文本。

## 选择原因

运行时邀请符合当前插件的内存运行时边界，不扩大 `rooms.json` 的持久化契约，也能明确告知重启后的失效行为。一次性消费和房间创建放在同一串行边界内，可以覆盖重放与并发接受。单独的 `CreatorUserId` 和 `IsSelfService` 保留现有管理员房间语义，避免用字段名称推断普通用户权限。

## 已知代价

- Emby 重启会使尚未接受的邀请失效，用户需要重新生成。
- 多实例或进程级横向扩展不在首版范围内；邀请码状态只在当前插件进程有效。
- 速率限制是进程内限制，不替代反向代理或账号级安全策略。
- 任何成员替换、持久单人房间和多人房间都需要另行设计契约。

## 后续影响

实现需要保持旧 `rooms.json` 可读：缺失的 `CreatorUserId` 回退为 `AdminUserId`，缺失的 `IsSelfService` 按 `false` 处理。新增测试应覆盖邀请码生命周期、房间创建原子性、旧房间读取、权限边界、并发接受和重启失效；真实双账号验收覆盖创建、接受、同步、暂离/重入、结束和再次创建。

## 验证依据

- 当前双人房间约束与退出语义：`src/EmbyWatchTogether/Room.cs`、`RoomStore.cs`、`RoomManager.cs`。
- 当前服务权限和嵌入式页面边界：`src/EmbyWatchTogether/WatchTogetherService.cs`、`Web/Configuration/watchtogether.html`、`watchtogether.js`。
- 后续实现与验收：`tests/EmbyWatchTogether.Tests/` 中的房间、服务、页面和新增邀请测试。
