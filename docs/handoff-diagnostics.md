# 换集诊断日志

本文是开发者当前参考，说明现行换集观测日志的字段、计数口径和证据边界。日志字段仍由当前产品实现；下方只把 S110/S111 的部署与调查过程标为历史，不把诊断能力写成根因修复结论。

## S110/S111 部署与调查记录（历史）

原 S110 本机产物、历史部署 receipt 与只读取得的 NAS 安装 DLL SHA-256 一致，为 `513dda4032d3c06c1d66091610e83e5569fcc810c2982abb05aed2adcb36d535`。S111 已将原候选源码收录为 `98ace2b`。这些事实只证明候选与诊断记录的身份关系，不代表重复跳集根因已确认或修复；当前排期见 `development-roadmap.md`。当时版本为 `1.6.0.5`，该 Stack 只增加换集观测日志，不改变播放决策、重试时序、命令参数或内存事件。

## 日志字段

新增行统一以 `WT_HANDOFF` 开头。日志中的 `operationHash` 由房间标识、handoff 开始时间的规范 UTC `O` 格式和目标 Item 标识计算；同一 handoff 的生命周期事件应共享该值。`requestHash` 由房间标识、目标会话标识、目标 Item 标识和该次调用使用的规范 UTC 时间计算，用来把引擎的一次逻辑尝试与内置 issuer 的实际调用边界关联起来。

标识只以短 SHA-256 或 `userA`/`userB` 别名出现。事件使用固定白名单，错误只保留稳定分类；未知错误归一化为 `unknown`。新日志不写入原始 room、user、session、Item、URL、路径或异常正文。已有普通日志和异常日志的行为保持不变，因此不能把整份 NAS 日志都视为脱敏日志。

字段中的 `atUtc` 沿用该事件传入的引擎 UTC 时刻；`dispatch_result` 也沿用同次调用的 `now`，实际调用耗时看 `durationMs`。日志自身的服务器写出时间以日志行前缀为准，不能把它当成新的命令返回时间。

事件含义如下：

- `handoff_started`：创建新的换集操作，包含 generation、目标和两端会话 hash。
- `target_superseded`：旧目标在创建新目标前失效。旧目标的事件先写出，再创建新的 handoff。
- `session_rebind`：主控或被控会话身份变化，包含变化后的 generation 和新旧会话 hash。
- `attempt`：引擎准备调用 `IPlayItemIssuer` 的一次逻辑尝试。`attempt` 使用现有 `RetryCount`，不能代替实际发送次数。
- `issue_result`：issuer 返回后的结果。`accepted=true` 只表示 issuer 返回接受，不表示客户端已经打开或执行目标 Item。
- `dispatch`：内置 issuer 即将调用 `SendPlayItemAsync` 的服务器侧本地调用边界，表示一次本地尝试，不表示客户端已收到命令。
- `dispatch_result`：该调用返回、超时或抛出异常后的稳定结果。`returned` 只表示本地调用返回，不能证明客户端收到或执行了命令；`timeout` 表示结果未知。
- `confirmation_timeout`：被控会话在当前 pending 期限内没有确认目标 Item。该事件关联最近一次已记录的 request hash。
- `target_confirmed`：确认快照中的参与者会话已位于当前目标 Item，记录位置、暂停状态和 handoff 年龄；事件发生在清理内存 handoff 之前。若没有可关联的已记录 pending 时间，request hash 为 `none`，例如跳过发送或此前未获得成功返回；不能仅由 `none` 判断从未调用过 PlayItem。
- `failed`：清理失败 handoff 之前记录稳定失败原因。

## 如何计数

`attempt` 是同步引擎的逻辑尝试数，`dispatch` 是内置 issuer 实际进入 `SendPlayItemAsync` 本地调用边界的次数，二者不能混用。每条 `dispatch` 最多对应一条 `dispatch_result`。验证拒绝发生在现有参数、会话和能力检查阶段，不会产生 `dispatch`。

内存诊断事件会按既有规则去重，不能用来统计每次真实调用。要统计一次换集进入了几次服务器侧 PlayItem 调用边界，应在完整日志中按 `operationHash`、`requestHash` 和 `dispatch` 事件计数，并用 `dispatch_result` 判断调用是返回、超时还是失败。

若完整日志中没有对应 `dispatch`，只有在确认日志完整且 logger 正常工作的前提下，才能判断该次流程没有进入内置 `SendPlayItemAsync` 调用边界。缺少日志、logger 初始化失败或日志被截断时应视为证据不可用，不能据此断言客户端没有收到命令。

`target_confirmed` 的 request hash 只关联最近一次已记录的尝试，不能单凭它确定是哪一次请求导致客户端打开了目标 Item。日志仍需和被控端的播放证据按时间、会话和 Item 对齐。

## 一次手动双端复现

1. 记录服务器当前加载的插件程序集版本和 SHA-256；分别记录主控和被控客户端版本。插件运行在服务器上，客户端版本单独记录。复现时以实际部署版本和可取得的客户端证据为准。
2. 让主控和被控都打开同一源集，保持双方处于可观察状态。
3. 只在主控执行一次下一集操作，等待一个完整的换集窗口结束，不连续点击或手动纠正被控端。
4. 保存覆盖操作前后完整时间窗口的服务器日志，至少包含 `handoff_started` 到 `target_confirmed` 或 `failed` 的全部 `WT_HANDOFF` 行，以及同一窗口的既有服务器异常日志。
5. 记录主控实际目标集、被控最终打开的集数、是否发生自动下一集，以及两端客户端日志中可取得的时间戳。
6. 在需要重复时重新开始一个独立操作，并记录新的 `operationHash`；不要把多次复现的行混在一个操作中统计。

被控端应尽量收集以下可取得的证据：是否收到 `PlayNow`/播放指定 Item 请求、请求中的旧/新 Item 和播放会话标识、播放器停止或结束事件及其原因、结束事件关联的 Item/会话、以及自动下一集触发记录。不同客户端的日志字段和保存位置可能不同，必须以实际可取得的客户端证据为准，不在此文档中猜测日志路径。

复现时应同时保留成功和失败记录作为对照，不要求失败必现。一次 `2026-10-08` 的 NAS 只读观察中，未改变环境就成功完成了一次换集：`22:41:52.466` 记录主控切到第 8 集，`22:41:56.404` 被控开始第 8 集，`22:41:58.090` 进入 `Watching`。从 handoff 开始到被控起播约 `3.938` 秒，到进入 `Watching` 约 `5.624` 秒，未出现片尾停止或自动跳到第 9 集。该成功样本只能说明同一环境下存在成功路径，不能单凭等待时长或该样本认定失败原因；应与失败窗口一起按上述字段对齐。

S110/S111 停点只准备了诊断能力，未声明已部署、未声明已完成 NAS 重启，也未确认客户端根因；这些是历史边界。当前发布与验收状态由 `development-roadmap.md` 和 `client-compatibility.md` 维护。
