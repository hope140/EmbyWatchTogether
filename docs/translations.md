# Contributing translations

The embedded page keeps its translations in `src/EmbyWatchTogether/Web/Configuration/watchtogether.js`. Chinese source strings are the keys. The translated dictionaries are `en`, `zh-Hant`, `ja`, `ko`, `ru`, `fr`, and `de`. Static HTML text and attributes are translated when the page is initialized; dynamic labels, messages, and dialog text use `t()` when created. User-supplied room and media names are not translation keys.

To add a language:

1. Add a locale dictionary alongside `translations.en`, using the same complete set of Chinese keys. Preserve placeholders, punctuation and any HTML semantics in context; inspect each use rather than translating fragments in isolation. Missing entries fall back to the Chinese source string.
2. A dictionary keyed by a language subtag also matches its regional tags, such as `ja-JP` or `fr-CA`. Extend `currentLocale()` only if the language needs a mapping beyond its primary subtag. It first tries the host's `globalize.getCurrentLocale()`, then `data-culture`, the document's `lang`, and the browser language. Traditional Chinese tags such as zh-Hant, zh-TW, zh-HK and zh-MO select Traditional Chinese; Simplified Chinese tags select Simplified Chinese. Unsupported languages use English. The controller checks the language whenever the page resumes; reopen or refresh after changing the host language.
3. Extend locale tests in `tests/ui/specs/watchtogether.spec.js` for the new locale. Check dictionary completeness, placeholders, dynamic states, dialogs, and narrow layouts. Run `npm ci` and `npm test` in `tests/ui`. Check the page in a real Emby host where possible.
4. Update the interface-language sections of both READMEs and submit the translation for review. When embedded HTML or JavaScript changes, update the page/controller cache keys and their tests together, as required by the repository's existing resource registration.

Fixed playback notifications are translated separately in `src/EmbyWatchTogether/NotificationText.cs` for each recipient. The server uses the account language saved when the page opens, not an inferred player language; accounts with no saved preference use Chinese. Add translations there for every fixed notice, update the allowed languages in the preference store and API, update automatic room-name prefixes for the creation language, and test each recipient separately. An absent or unsupported creation-language value defaults to Simplified Chinese; invitation rooms use the accepting page’s language. Administrator-written messages are passed through unchanged; update broadcasts to administrator sessions are separate and remain Chinese.

The dictionaries stay in the controller and use Chinese source text as keys. Some dynamic sentences are assembled from translated fragments; review those combinations in context when adding a language. A separate resource file, semantic message IDs, and complete parameterized messages would make larger translation sets easier to maintain, but would require a coordinated resource-loading change.
