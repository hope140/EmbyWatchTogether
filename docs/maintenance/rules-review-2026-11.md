# 协作与发布规则审视（2026-11-16）

范围是仓库自设规则、文档索引和发布流程；平台权限与安全政策独立适用，不由仓库文档放宽。本次以 beta 的 `v1.7.3.1` 源码为基线，不修改发布、合并、标签或安全门禁。`LOCAL_OPERATIONS.md` 和仓库 `.agents/skills` 在本次环境中不存在；没有推断其内容。

## 来源和判断

- [`AGENTS.md`](../../AGENTS.md) 为全仓库职责、授权及审核入口；[PR Stack](../pr-stack-workflow.md)、[模型策略](../ai-model-policy.md)、[验证与交接](../validation-and-handoff.md)分别细化执行方式。`6cd5800` 已集中整理这些入口，低风险任务允许主线程单代理闭环。执行时仍须服从当前用户指令及运行时能力，仓库中的模型候选不证明实际可用。
- [版本规则](../versioning.md)和[发布请求](../release-requests.md)定义约定；[release workflow](../../.github/workflows/release.yml)、[请求控制器](../../scripts/release/release-request.cjs)及其测试才是实际自动门禁。历史缘由见 [ADR-004](../adr/004-reviewed-release-requests.md)：在当时工具缺少 tag/dispatch 接口的条件下，专用 PR 提供可审核的源码、CI 和发布内容绑定。保留签名、固定来源、版本一致、不可覆盖和失败关闭约束。
- 发布与验收不是同一证据：[1.7.3.1 说明](../releases/v1.7.3.1.md)记录界面语言和房间名称已验收，播放通知及菜单语言宿主行为仍待实测；1.7.3.2 内部预览不等于公开签名资产。

## 供维护者决定的调整

1. **Stack 计划和代理派发**：建议把完整字段表限定于确有多任务依赖、共享资源或高风险的工作；单个文档/小修复继续用简短范围、验证和回滚说明。保留真实隔离、文件所有权与完整 diff 审核。现有规则已有低风险例外，但“复杂”未定义，容易重复列无关字段。此项可在后续规则修订中明确，不影响平台是否允许派发。
2. **模型和服务模式**：建议把易过期的具体型号、档位及固定 Standard/Fast 约定改为可选的维护者偏好，并以当前运行时与用户指令为准；保留按风险选能力及审查责任。当前候选表和旧固定 worker 名称并不一致，且无法证明当前服务模式。变更前请维护者确认成本和偏好。
3. **正式版版本段**：是否允许仅第四段变化的 stable 热修复？当前 [版本规则](../versioning.md)和发布 workflow 都禁止，须同步设计版本选择、自动更新和测试，不能只改文字。现有规则简化 stable/beta 辨识，但会增加小型正式修复的版本号成本。
4. **发布请求和 tag**：建议保留现有固定 SHA、CI、签名、不可移动 tag 和不可覆盖资产；若现有工具已支持受控手动发布，可评估将专用请求作为可选路径。ADR 的工具限制是当时事实，替代流程必须先证明相同授权、审计和失败处理，再单独修改 workflow 与测试。不要删除历史请求或重用已有 tag。
5. **合并与安全授权**：建议保留用户明确授权、按风险验证和敏感信息保护。合并专用发布请求会触发发布，不能当作普通文档合并；若想改变审批或保护规则，应先确认实际仓库设置和责任人，单独审查。

本次仅修复过时版本入口、验收边界及重复历史索引，并纠正手动发布与请求发布的不同 tag 步骤；上述建议均未生效。
